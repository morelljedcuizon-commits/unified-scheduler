# Implementation verification

Initial verification on October 30, 2026 used Windows 11, Python 3.14.7, PySide6/Qt 6.12.0 and PyInstaller 6.22.3. Later checks are dated below.

Website validation was completed on October 31, 2026. The original October 30 app/package checks used no real provider credentials; subsequent installer and sign-in checks are recorded separately.

The developer subsequently confirmed that the API works and testing is complete, and authorized website publication on October 31. Live provider tests below describe the limits of this agent's earlier checks, not a request to repeat the developer's completed testing. The website draft notices were removed and the website is now published.

## Completed checks

- November 1 Google sign-in fix: a developer-completed live diagnostic reached the callback, received HTTP 200 from Google's token endpoint with all requested Calendar scopes, then failed the signed identity token's issued-at time check. A fresh Google HTTPS time comparison showed this Windows clock about 3 seconds behind. Version 1.0.1 passes Google's verifier a fixed 60-second clock tolerance and gives Windows time-sync guidance for larger time/expiry failures. Signature, audience, issuer, nonce, verified-email and Calendar-permission checks remain enforced. Diagnostic output contains only stages and exception types; no tokens or account data were persisted by that diagnostic.
- November 1 scope regression fix: actual OAuthlib token parsing rejected valid changed/legacy grants before the provider's permission checks could run. The Desktop flow now accepts only OAuthlib's parsed scope-change warning and preserves the returned grants for application validation. It does not retry the code exchange or change process-wide OAuth settings.
- **141 tests passed** in the November 1 complete suite (26.21 seconds), including 18 actual token-response parsing cases and 9 real signed-JWT cases covering small clock drift, excessive drift/expiry and invalid identity boundaries.
- November 1 packaging: the Google-enabled 1.0.1 frozen application passed its isolated demo startup check. Distribution inspection, installer compilation/version metadata, portable ZIP integrity and both SHA-256 checksums passed. ## Checks requiring user accounts or an interactive Windows session

Actual Google authorization, real account calendars, revoked consent and token expiry must still be tested with the developer's legitimate Desktop OAuth client and allowed Google users. Private Moodle subscriptions require user-supplied URLs. No real Google account or Moodle feed was authorized during development.

The October 30 candidate ZIP was deliberately **local/Moodle-only** because no real Desktop OAuth client had been supplied at that time. The October 31 v1.0.0 installer and ZIP include the subsequently supplied Desktop client; their packaging checks do not claim live Google authorization or verification approval. The manual Windows/GitHub Actions workflow was prepared but not run in GitHub; its Windows/Python 3.12 runner remains an external check. Google Cloud was last reported as External / Testing and was not accessed. No Production switch, domain verification, branding approval or sensitive-scope approval is claimed.

Notification display can be suppressed by Windows settings; end-to-end notification delivery and sign-in startup have not been manually verified. Startup registry command generation is covered by a mock test and does not enable startup during tests. A clean-machine run without the development environment and high-DPI scaling checks remain part of the [manual verification checklist](manual-verification.md).

Google and Moodle are read-only. Notifications require the app to remain running. The executable is an unsigned portable folder build; distribute its entire folder rather than the `.exe` alone.
